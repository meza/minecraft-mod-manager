# Packaging and release readiness

Use this guide when preparing release artifacts or assessing the Go-port release baseline.
Ordinary documentation, product and code contributions use
[CONTRIBUTING](../../CONTRIBUTING.md#verification); they do not run the release workflow merely
because it is documented here.

## Package artifacts

Use `make dist` to package existing build outputs into
`dist/mmm-<os>-<arch>-<version>.zip` (version defaults to `dev`). The output includes
`dist/metadata/THIRD_PARTY_NOTICES.txt` and `dist/metadata/mmm-sbom.json`, generated by
`make notices` and `make sbom`; these metadata files are not inside the zip files.

Use `make prepare` for both build and packaging. Distribution builds need the API token defaults
described under [using your own API keys](../../README.md#using-your-own-api-keys). Inject release
credentials without exposing them in commits, output or logs.

## Release readiness for 3.0

[Product intent](../intent.md) defines the Go-port release behavior; the
[command guides](../commands/README.md) explain operator workflows. Historical feature-parity
claims alone do not establish conformance to the intended product.

Before release:

- Survey all command error paths before finalizing error-remediation scope, including paths
  outside existing scenarios. Verify that version-constraint failures identify the relevant
  constraint and differ from missing projects and network failures. Include the previously
  reported connection-timeout problem if it remains present.
- Obtain the 2025-12-19 independent audit report from the project owners, then resolve its findings
  or obtain their explicit acceptance of remaining findings. If the report or evidence of resolution
  or acceptance is unavailable, this release requirement remains unverified. Do not infer that the
  findings are already resolved.
- Demonstrate the acceptance journeys in product intent, including manifest-cache outage recovery
  and proxy behavior. Both remain in the 3.0 baseline.
- Verify CI on pull requests and pushes, and semantic-release automation on release branches.
  The pipeline must produce and publish the documented Windows, macOS and Linux archives,
  containing `mmm.exe` on Windows and `mmm` on macOS and Linux.
- Run validation in the actual release context. A dry run must demonstrate the expected artifacts
  and workflow before publishing, alongside evidence that the release requirements are met.

Historical parity work also mentioned update notifications without defining their behavior in
product intent. Obtain an explicit product decision about that item before release; do not silently
drop it or infer a new product contract from the old parity label.
